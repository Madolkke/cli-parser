## 模型行为与失败证据

LLDP L3：根汇总与两个重复实体、嵌套章节都保留，最终严格差异来自
`/neighbors/*/vlan_id` 的业务前缀被移到模板字面量；字段仍为合法 string，
Schema 无法发现。最终提交 S2 span `00000000-0000-0000-82f0-5fc33260ce45`，
UI 完整 records 确认该前缀丢失。不是根起点修复失败的直接证据，也不是新指导
改善字符串保真的证据。未实现额外字符串修复。

LLDP L4：S1 仍截短分隔行，根数组缺失，说明模型不总遵循完整行要求。
对应 span `00000000-0000-0000-e4f8-169a8ce82de9`；S2 后根恢复，又出现
MED 必填缺失；S3 改后缺 description；S4 最终严格通过。这一序列证明
“修正根起点”与“整体正确”是不同层次，不能只统计 Schema 错误总数。
其他根数组拒绝中未逐项确认的起点因果记为未知，不全部归入根机制。

Power P1：S1 已使用覆盖完整表头的根起点并 accepted，随后在根警告捕获上
反复修改。S1–S5、S7–S10、S14 accepted；S6 Schema 拒绝，S11–S13 非 object
拒绝。最终 S14 使用独立根警告组但未匹配该行，完整 records 缺 `/warning`。
最后实际请求明确包含 optional_paths_absent `/warning`、remaining_submissions=4
及完整 records；随后 finish。最终提交 span `00000000-0000-0000-b134-d75455d26a8d`，
实际请求 span `00000000-0000-0000-5a96-2540b3edcb24`。不能归因为反馈丢失，
也不能把该 trial 的全部耗时归为根起点；根警告行匹配和复核选择仍是独立问题。

已确定的机制数量按证据下限报告：v39 根截短误用至少 1 trial/1 提交（L4 S1），
该 trial 最终通过；最终失败中 LLDP 符号清洗 1 trial/1 提交，Power 根警告缺失
1 trial/至少最终 1 次提交。其余提交是否存在相同内容差异未全部逐条 UI 核对，
不补零、不将同类诊断自动等同为同一根因。
