# Easy / Medium 扩展回归失败诊断：2026-09-13

## 范围与结论

分析对象为 [本轮回归](easy-medium-extra-v38-regression.md) 的四次严格失败。
产品仍为 v38，本次仅进行只读诊断，没有修改产品、测试资产或运行新的真实 trial。
Trace 正文仅在 Laminar UI 审阅；本报告只保存字段路径、结构事实、计数、标识和机制结论。

总体严格通过 56/60；原有 Easy/Medium 仍为 32/32。
四次最终失败均为字符串取值边界差异，各有一个最终字段不同；没有缺字段、类型错误、worker 失败或未 finish。
因此不能把这批结果解释为原有 Easy/Medium 整体劣化，也不能把中途 Schema 拒绝当作最终失败原因。

## 最终差异与提交过程

Trial 从 1 编号。以下与当前资产的严格取值约定比较，不复制解析值。

| 用例 / trial | 提交数 / accepted 数 | 最终差异路径 | UI 核实的机制 |
| --- | --- | --- | --- |
| Juniper / 2 | 1 / 1 | `/users` | 用户数字段包含尾随标签；模板主动把标签纳入捕获范围 |
| Juniper / 3 | 1 / 1 | `/cli_uptime` | 运行时长包含引导前缀；前缀被纳入捕获范围 |
| Juniper / 4 | 2 / 2 | `/users` | 首次逗号边界错配，将部分运行时长分入用户数字段；第二次修正跨字段错配，但仍保留用户数标签 |
| Arista / 2 | 5 / 1 | `/model` | 最终根对象和必填字段齐全，但型号包含厂商前缀 |

Juniper 三个失败 trial 共四次提交，均通过 Schema；其中 `/users` 标签保留涉及两个 trial、三次提交，
`/cli_uptime` 引导前缀涉及一个 trial、一次提交；另有一次提交同时发生时长与用户数的逗号边界错配。
这些是重叠机制计数，不能相加作为独立失败提交数。

Arista 的五次提交依次为：

1. 根起点使用无特征整行捕获，返回 `ttp.invalid_record`，没有可验收根 record。
2. 增加匹配后的排除过滤器，仍缺少大量必填字段，返回根路径 `required` 诊断。
3. 改为带锚点的正则起点，仍缺少必填字段，包括型号。
4. 将完整候选缩减为三个字段，明确因缺少其他必填字段被拒绝。
5. 使用匹配阶段的行特征约束后得到完整根对象，通过 Schema；型号取值边界仍与约定不同。

这条 Trace 同时暴露结构修复成本与内容复核不足。前三次的 TTP 内部匹配细节没有在本轮进行合成复现，
因此只能认定上述模板变化与输出结果的对应关系；不能仅凭 Trace 将所有中途缺字段归于同一个底层机制。
第五次与首次相比恢复了结构，最终严格失败则直接定位到型号边界。

三次独立测试均围绕根匹配展开：前两次使用与相邻失败提交相同的完整文本及候选，
第三次移除输入空行并调整显式起点。它们没有检验型号应否包含厂商前缀这一语义约定；
parse-only 结果也不等同于 Schema 验收或严格内容正确。

## 为什么确定性反馈没有拦住

这两个用例的相关 Schema 属性均只有 `type: string`，没有字段说明。
当前标准答案隐含了更细的边界约定：用户数字段不含标签、运行时长不含引导前缀、型号不含厂商前缀。
这些约定有原文结构依据，但模型接收的 Schema 没有完整表达。

因此存在两个层次的问题：模型捕获和复核没有稳定采用这些边界；资产的语义契约也不足以消除歧义。
特别是厂商加型号与仅型号，两者都是可理解的字符串表达。不能把严格不一致全都等同于模型凭空编造或遗漏信息。
保持原文业务字符串的产品指导本身不要求保留标签；没有受控对照证据证明 v37/v38 导致此次边界选择。

`required_paths_complete=true` 只证明必填路径齐全，`accepted=true` 只证明确定性验收通过。
它们不会比较标准答案，也不能识别标签被混入字符串。这是现有协议的边界，不是校验器漏执行。

UI 已对照 Juniper trial 2、trial 4 和 Arista trial 2 的最终工具结果及下一次实际模型请求：
完整反馈与相关 records 均到达模型，随后调用 finish；不是最新反馈被历史折叠掉。
Juniper trial 3 已核实提交结果，未逐字核对其下一轮请求，不能据其他三条外推为四条均完成此项检查。

全批次 worker 错误和压缩均为零，60/60 均有候选并 finish；四个失败也未因预算终止。
Juniper 三条分别耗时 54.28、52.03、167.66 秒；Arista 耗时 474.53 秒。
增加预算不能直接向模型提供缺失的语义约定：Arista finish 前仍有 13 次提交额度。

## 建议优先级

1. **先补清 Schema 字段语义。** 对存在边界歧义的字段使用当前门禁已经允许的 `description`，
   明确标签、厂商前缀、单位和时间引导词是否属于值。说明必须由原始输入及预期业务用途独立审定，
   不把本轮 Trace、解析值或标准答案正文回灌模型，也不为本次错误修改 expected。
   这是覆盖四次最终失败的共同优化方向，但本轮没有评测其效果，不能保证四次都会修复。
2. **补通用值边界合成测试。** 包含值内逗号、尾随计数标签、厂商与型号、应保留的业务符号和单位；
   同时验证正确结果与“Schema 可通过但内容错误”的对照。由此区分字段契约不清与模板匹配不稳。
3. **再单独优化根匹配指导。** 为 Arista 所暴露的整行匹配、匹配后排除与匹配阶段限制建立单因素实验，
   确认机制后才调整产品提示。该方向主要减少中间失败与耗时，不直接解决最终型号语义。

不建议本轮继续加预算、放宽严格评分或添加按字段名自动清洗的后处理。
当前证据支持优先治理字段语义和边界，尚不支持归因为 v38 拼接指导回归。
