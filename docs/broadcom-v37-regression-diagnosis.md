# Broadcom v37 回归偏差诊断

2026-09-10。只读分析既有评测和 Laminar UI，未启动新模型评测，未修改产品或评测资产。

## 结论

本轮四次最终失败均定位到 `/additional_packages` 的拼接分隔符：模型使用换行，
标准 expected 使用单个空格。内容项及顺序保留，四次叶子 precision/recall 均为
11/12；这是一个字段的表示方式偏差导致整条 record 严格失败。

最强的提示层嫌疑是 v34 新增的多行自由文本保留换行指导及示例，而非已证实的
v37 单次改动回归。深层问题是纵向多值列表与多行自由文本的分类、序列化约定不够
明确。冻结 Schema 对该字段只有 string 类型，没有表达拼接约定。

## 改动关联与证据强度

1. **已证实的直接机制：** 同一字段使用了不同于 expected 的分隔符；严格深度比较
   不忽略字符串内部换行。因此全部字段都有值、Schema 通过仍然可以严格失败。
2. **最强待验证因果假设：** `ee1c647`（v34）将原有折行/多值两类规则扩为三类，
   新增多行自由文本保留换行的文字及 notes 示例。当前提示第 238–258 行和
   第 429–430 行仍包含该指导。模型可能把纵向列举的多值集合归为多行自由文本。
   该解释与四条模板选择及 Trial 2 的复核判断一致，但没有单变量实验验证。
3. **v37 不是已锁定根因：** `a28e66a` 主要调整可选 string 状态、空槽及值内符号
   的保真指导，没有修改 joinmatches 分隔符规则。它可能进一步增强字面保真倾向，
   但这层影响目前只有假设；不能因最新版本号为 v37 就归因于 v37。
4. **反馈的能力边界：** required/optional 覆盖事实检查键是否存在，类型校验确认
   string。两种分隔符均满足同一冻结 Schema；没有权威规范时无法从这些确定性
   事实生成“应改为空格”的诊断。更多 Schema 错误反馈不会直接解决此问题。

## 建议顺序

优先明确通用的字符串表示规则：区分同一 token 的视觉折行、纵向列举的多值集合、
本身具有行界语义的自由文本，并为三类提供平衡的合成对照。只看到物理换行不足以
认定需要保留换行；业务词项内部的空格和符号仍需保留。

同时核查产品要求是否确实将纵向列表的 string 表示规范化为空格。如果这是产品
契约，应向模型明确表达；当前 Schema 的 string 本身不能传递该约定。若没有此
契约，严格分数下降也暴露了评测隐含规范与模型可见要求之间的缺口，不能将其全部
解释为业务信息丢失。本次保持既有标准答案及评分规则不变。

后续因果验证建议只替换这段指导，保留其他配置，以 Broadcom 与真正需要保留
换行的用例一起回归，避免修复一个用例后破坏自由文本。不要全局删除换行，也不要
将字段名或本轮 Trace 内容写入产品提示。上下文保护、finish、预算等继续独立处理。

本报告只保存字段路径、结构事实、数值、提交及 Trace/span 标识，不保存 Trace
正文、模板、records、输入或内容哈希。SQL 仅查询 span 标识、名称、类型和时间。
