# 近期 Schema 优化审计：收益、瓶颈与证据边界

审计日期：2026-09-16。覆盖 v40、v41、v42、v43 提示及回退、Schema 工具与冻结流程、
受限校验器、评测和审阅指标、合成测试，以及 v43 安全运行事件和用量。
本次未修改产品、评测资产或运行新模型。正文读取仍遵循原 UI 限制；v43 的完整业务
语义尚未审阅，不能声称已确定其每份提案的错误原因。

## 结论

近期并非完全没有改善，而是**局部改善尚未形成可保留的综合改善**。主要障碍是：
完整契约需要稳定的建模政策，但当前仍让模型自由决定多个维度；结构验收后立即冻结，
缺少业务合理性反馈；提示实验各自从 v40 出发，已观察到的收益没有累积。
此外存在可离线复现的无效工具调用循环，以及需要核实的供应商输出预算适配问题。
不能把这些不同问题都归因于提示不足或推理时间不够。

## 1. 完整契约目标与建模自由度不匹配

当前提示有原则，却没有固定各项决策的优先级。v43 明确不强制同级或嵌套；命名只要求
语义明确和合法字符；容器名、组织形式、数字类型、required 和额外约束仍有多个合理解。
同样合理不意味着字段、层级、类型、required 和约束全部一致。

v43 有 74/81 对的路径集合不同，只有 7 对同路径、5 对同结构、3 对同契约。
路径差异可能来自命名、父容器变更、移动、遗漏或拆分，不能全部叫作同义改名。
排除 MOS 后 v43 仍是 3/78，v40 为 8/78，因此一次失败不能解释普遍漂移。

另一方面，平均路径重合度 v40 为 53.1%、v43 为 59.6%。局部更接近与整份完全一致
是不同指标，不能说 v43 所有维度全面退化。拆分目标是否改善也不能只靠字段数判断。

相关源码：`agent/prompt.py:38–71`；契约比较 `evaluation.py:2616`。

## 2. Schema 阶段只有合法性修正，没有业务修正闭环

`workflow.py:650` 的校验只读取候选 Schema 本体，不以 command_outputs 判断业务
覆盖、根粒度或拆分；`agent/tools.py:843` 在校验成功后永久冻结。
本批 52/56 trial 只有一轮。模型第一次给出合法 Schema 后，通常没有业务反馈或第二次复核。

v42 OSPF 在两次结构拒绝后缩减成单字段仍被接受，是已有真实例证。增加轮数只有在
确定性拒绝时才会触发修正，不能自动让合法但不合理的方案变好。这是当前产品契约的
能力边界，不是此次新增代码偶然漏掉一次校验。

后续若增加冻结前复核，属于协议设计变更，不能在本次审计中直接实施；也不能假设
增加一次模型自检就足以解决语义可靠性。

## 3. 提示实验没有累积，且仍存在具体说明缺口

Git/AST 核对：v41、v42 均整体回退，v43 是 v40 加拆分指导，不包含 v42 的标签规则。
因此 v42 的命名收益没有进入 v43。单项实验有助归因，但“回退后换另一维试验”本身
不是一条累积改进路线。不能无验证直接叠加所有旧提示，也不应把整体回退解释成每条规则无效。

明确缺口：提示要求 Draft 2020-12，却没有告知项目完整受限关键字集合；校验器禁止
$id、$defs、$ref、pattern、format 等。历史拒绝记录证明模型确实会提交这些标准能力。
这是提示与实际工具契约的说明不一致，值得先修；不能未经正文确认就当作 MOS 根因。

静态审阅还发现待消歧处：允许省略 required 与“全部实例出现就必填”的政策未明确区分；
“每条 array 的字段都稳定得到”与允许可选字段的表述存在张力；拆分示例已给出子标签，
对隐含复合边界的迁移证据弱；两组局部合成输入未显式标注为不同输出，可能干扰实体边界。
这些属于可改进的说明问题，不是已经证实造成真实退化的因果结论。

相关源码：`agent/prompt.py:30–107`、`validation/json_schema.py:27–79`。

## 4. 工具调用无进展循环是可复现的工程问题

MOS #2：26 轮、393.078 秒、0 次进入 Schema validator、26 次工具结果；HTTP attempt
均成功，没有网络重试。累计输入 1729496 Token，占全批 88.8%。工具 span 只有 1 个。

框架在产品工具之前执行 JSON repair 和工具入参校验；失败产生 ERROR ToolResult，
不会进入产品工具 span。产品内参数门禁拒绝则会产生 span，但不增加 schema_submissions。
因此不能把 26 次调用叫作 26 次 Schema 内容校验失败。

runner 在观察到正确工具名时就重置 no-tool 计数，随后 ERROR 仅累计统计，没有独立
连续无进展止损。离线复现可稳定得到 26 次调用、26 次 invalid、0 submission、0 no-tool
retry，最后耗尽轮数。真实 MOS 参数具体形态尚未知，不能套用合成错误正文作归因。

阶段事件 agent_round_limit 表示停止条件，最终 model_submission_tool_call_invalid
是 workflow 的失败分类，两者不矛盾。应分别保留，而不是挑一个当作唯一原因。

相关源码：`agent/runner.py:580–610`、`agent/tools.py:785–822`、`workflow.py:939`；
框架 `.venv/Lib/site-packages/agentscope/agent/_agent.py:1613`。

## 5. 运行配置需要验证到供应商实际语义

v43 85 次模型调用中，10 次观测 output_tokens 超过 8192，最大 63032。
产品把 max_tokens=8192 交给 AgentScope，锁定依赖实际发送 max_completion_tokens。
当前证据只能说明 8192 没有体现为观测输出总用量上限，不能直接断言供应商忽略参数、
发生截断或某种计费机制。下一次优化前应核对实际请求的有界参数、供应商参数语义与用量口径。

两阶段实际使用默认 OpenAIChatFormatter，ThinkingBlock 被跳过，产品计数也排除它。
MOS 输入增长不能直接归因于旧 Thinking 计数问题。输入从 2306 增至 94480 的具体
内容来源仍需正文或严格受控的消息结构证据。

相关源码：`agent/builder.py:116`、`agent/model_attempts.py:261`；锁定依赖
`model/_openai_chat/_model.py:227`、`formatter/_openai_formatter.py:339`。

## 6. 工程通过、模型遵循与效果提升是三种证据

v43 示例测试验证预写 Schema 能描述预写 records，模拟 transport 验证提示到达与阶段隔离。
这些工程测试必要，但不会证明模型面对新文本能作出正确拆分。1137 项通过不能替代真实语义审阅。
本次独立复验契约指标测试 45 项及协议测试 3 项均通过，未发现指标计算错误足以解释退化。

每例只有 4 份提案，一份变化能影响 6 对中的 3 对，84 对不是 84 个独立样本。
同版本 v40 两批结构一致也从 16/84 变为 12/84，已有自然波动证据。
历史对照、未版本固定的资产、没有同期交错对照及独立盲审，使两三份提案的变化难以做因果判断。
这不推翻用户采用门槛；门槛用于是否采用，机制结论需要另有证据。

当前审阅器验证 ID、枚举和内部一致性，不能证明人工业务判断可靠。初版 v40 曾允许
insufficient_evidence 与 acceptable 并存，新版明确禁止；跨旧报告需标注口径变化。
全部近期 Schema-only 都没有执行 TTP，“合理且可解析”的后半目标尚无测量。

## 建议的下一步顺序

1. 收尾 v43：补齐合法授权范围内的正文审阅，区分目标拆分变化与其他漂移，完成既定回退和结果提交。
2. 优先修确定问题：受限 Schema 子集说明、互相含糊的 required 表述、工具边界统一反馈与连续无进展止损；先核实供应商参数实际语义。
3. 先设计统一决策次序，再改提示：实体归属→独立值边界→字段组织→命名→类型→required→约束；为每个允许多解处选择默认，不只增加泛化原则。
4. 用独立合成材料检验模型实际选择，覆盖应拆、不可机械拆、边界不明确及重复实体；这是新增真实行为试验，不能伪装为普通离线测试。
5. 后续正式对照固定资产版本，采用同期对照或适当重复，并对新增错误与拆分争议独立复审；保持原门槛，不用统计解释掩盖失败。
6. 另设解析闭环评测，不能用 Schema 合法率或一致率替代可解析性。

本次不自动实施这些事项，也不将尚未审阅的 v43 合理性填为零或通过。
